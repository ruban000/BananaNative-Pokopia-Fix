# The Legend of Zelda: Ocarina of Time (`0400486024DEC000`)

A Switch 2 game: update v131072 (the dump's content version; no `control.nacp`, so no display version), SDK 22.2.8 built for the Switch 2 (`spec: Ounce`), NVN2 API 231.40. Nintendo EPD's engine (sead / agl / gsys, Havok, CRIWARE), modules `main`, `subsdk0` (NintendoSDK movie: the AV1 movies) and `sdk`; every NSO segment is ZBIC-compressed. **In bring-up: reaches the title screen on Android (2026-11-06)**, 60 fps over the title movie, with the menu's compute programs missing from the shader library ([Boot (Android)](#boot-android)). Not run on the Mac.

## Movies

- **What they are** (`ffprobe` and `trace_headers` over all 26): AV1 Main 8-bit 4:2:0, 1920x1080 at 60 fps, BT.709 matrix and primaries, sRGB transfer, limited range, no film grain, no audio track; encoded with SVT-AV1 and remuxed by QuickTime into Matroska. 1,394 s and 83,630 pictures in all, 1.64 GB, 2.8 to 21.5 Mbit/s. Each packet is a temporal unit without a temporal delimiter; every key frame packet repeats the sequence header (a key frame about every 5 s). From 9 s (the 8 `Dm_MelodyGet_*` jingles) to 311 s (`Dm_StaffCredit_0000`); `Dm_Title_*` are the title screen's background loops (99 s, then 30 s loops), on screen for as long as the player idles.
- **Who plays them:** the pack's movie module is `subsdk0` (NintendoSDK movie 22.2.8). The game's player (main +0x3b5f08c…) asks `movie::VideoDecoder` for NV12 pictures in plain buffers (output format 3, pixel storage type 1, w*h*3/2 bytes a frame, one image pool per `VideoFrame`); the movie library's wrapper (subsdk0 +0xf6d0…) picks the codec by the decoder kind at +0x400 (3 = AV1) and calls the 14 `nn::codec` AV1 exports of the sdk module, then `ReadDecoderOutputImageNv12`. It aborts on any error of the AV1 Initialize (subsdk0 +0xf900 / +0xf9c0), so without an AV1 decoder the first movie would end the game.
- **Status: plays on the phone (2026-11-06):** the title movie is decoded and presented at 60 fps, the Initialize taken is by transfer memory, about 9 ms of CPU a picture over dav1d's two threads ([Boot (Android)](#boot-android)). Before (2026-11-05): implemented, unverified on a device. The Android host decodes them with dav1d ([AV1 movies on SDK 22.2](../../../docs/reference/movies.md#av1-movies-on-sdk-222-implemented-unverified-on-a-device)): all 14 entry points of this sdk build are taken over, pictures are bit-exact with ffmpeg's dav1d in the Linux test (and on 90 packets each of `Dm_MelodyGet_Sun_05`, `Dm_Title_0005` and `Dm_StaffCredit_0000`, decoded by the wrapper by hand). (`DM_AV1_THREADS` belonged to that first wiring, replaced on 2026-11-08 by upstream's `hle_movie_av1.c`: see the movies entry.) Decode cost on one Ryzen 9 7950X core (ffmpeg's libdav1d, x86 assembly): 3.1 ms a picture (`Dm_StaffCredit_0000`), 4.4 ms (`Dm_Title_0075`), 6.4 ms (`Dm_Title_0065`, the hardest); on the phone measured since (above).
- **What the first boot should log:** `[codec] image pool 1920x1080 format 3, 1 picture(s)`, then `[codec] AV1 decoder 1: 1920x1080, input format N, output format 3, by transfer memory` (or `by remote memory`: which one the game takes is not known from the disassembly) `(dav1d, 2 thread(s) on the host)`, `[codec] AV1 decoder 1: first picture 1920x1080 into buffer 0`, and at the end of a movie `end of stream after N pictures` with N = 60 a second (570 for a 9.5 s jingle). No `[RED] nn::codec` line. A title loop shows a Flush or Stop and a new first picture, or a Finalize and an Initialize in the same memory.

## Window size and dynamic resolution

Read from the update's main (`e0f3ccfa…`, decompressed, 2026-11-06), then checked on the phone at the title (below). Three sizes: the nvnWindow textures, the output size the game crops them to and draws its 2D and upscaler output at, and the 3D scene's dynamic scale of the output.

- **Output size** (current). `main+0x112c5e0` (a method of the graphics settings object, its only reader) takes a u32 width, height pair from the table at `main+0x3f58540` (640x480, 720x480, 1280x720, 1600x900, 1920x1080, 2560x1440, 3840x2160) by the operation mode (`+0x547`: 0 docked, 1 handheld) and the graphics scale (`+0x54a`): docked, entry `6 − scale` (scale 0: 3840x2160, 1: 2560x1440, 2: 1920x1080); handheld, 1920x1080, or 1280x720 when bit 1 of `+0x2f8` is set. The two bytes come from `nn::oe::GetOperationMode` and `nn::oe::GetCurrentGraphicsScale` (`main+0xe376c0` / `+0xe376d8` at start, `+0x3bc0374` / `+0x3bc0394` on their notifications, stored by `+0x3bc02c4` / `+0x3bc02f4`). The host answers console mode and scale 1, so the entry is 2560x1440 (`main+0x3f58568`). The settings update `main+0x6502e0` then takes the smaller of that pair and its configured size per axis (`+0x6505ec`) and hands it on (`+0x1087f40`): **2048x1152 at the game's own size** (`WindowCrop 0,0 2048x1152` and a 2048x1152 RGBA target, run `20261106-105417`), 0.8 of the entry as on Mario Kart World.
- **Window textures.** Three of 2560x1440 (`WindowInitialize swap chain 3 textures … first 2560x1440`) whatever the entry says: the window object's float size (`main+0x112e514`, `+0x5280c0` on a resize) does not come from this table (not traced); the game crops them to the output size (`nvnWindowSetCrop`), and the host presents the crop.
- **`window_fn … pair`** (current). The profile names the entry; at load the host checks that it holds 2560x1440 and writes `DM_WINDOW_SIZE` into it ([`window_fn`](../README.md)). Run `20261106-104912` (`DM_WINDOW_SIZE=1920x1080`, the launcher's default): `window: 1920x1080 (DM_WINDOW_SIZE; the size table entry main+0x3f58568; the game's own 2560x1440)`, `WindowCrop 0,0 1920x1080`, a 1920x1080 target in place of 2048x1152, the screenshot 1920x1080; 59.7 fps at the title, no crash. A size above 2048x1152 cannot raise the output (the game's minimum per axis), and `DM_OPMODE=handheld` takes another entry the row does not touch.
- **Dynamic resolution** (current). The controller is `main+0x805aa0`. Its input is the GPU time of the frame: the frame timer singleton (`main+0x4e81dd0`, made by `main+0xf92500`, three per-frame timer objects in rotation) reads two timestamp reports per frame in `main+0x5a8f0` through `nvnDeviceGetTimestampInNanoseconds` (the pointer at `main+0x4c8dcb0`), takes their difference in µs (× 0.001) and its share of a 60 fps frame (× 100 / 16,666.67), and keeps 3- and 5-frame averages; the controller reads the share (`+0xc` of the singleton, ignored at 1000 % and above) beside a cost model of the scene (a least-squares fit over a ring of frames) and steps through a list of levels, each a scale rounded to the alignment at `+0x80` of the controller. The reports are the `TIMESTAMP_TOP` / `TIMESTAMP` pairs every command buffer of the engine records at its start and end (`main+0x5b178`, `+0x5ba90` and their siblings: buffers at `+0x80` / `+0x88` of the command buffer object). At `main+0x805bd0`, `tbz w8, #0, main+0x80640c` tests the controller's enable bit (`+0x188` bit 0); `main+0x80640c` is its own disabled path, which returns a scale of 1.0 (the full output size) and the last level's flags. The floor of 854x480 is Lichii's figure (below), not found in the code (likely a RomFS parameter).
- **`dynres_fn`** (current). Lichii (GPL-3.0, permitted for this project) has a built-in "Max Resolution" patch for this build (commit `99ac3d5955`, `src/core/file_sys/patch_manager.cpp`, `BUILTIN_PATCHES`: module `main`, build `E0F3CCFA…45DA3348`, offset `0x805BD0`, `0x360041E8` → `0x1400020F`), because on its GPU emulation the controller sits at its 854x480 floor. Checked here: the update's main holds `0x360041e8` (`tbz w8, #0, #0x80640c`) at `+0x805bd0`, and `0x1400020f` is `b #0x80640c` from there; the base's main holds something else there (`0x3900b669`). The profile's `dynres_fn` row writes the branch at load unless `DM_DYNAMIC_RESOLUTION=1` (the switch NieR:Automata's builds read, with the same default: full resolution): `dynamic resolution: off, full resolution (…main+0x805bd0 360041e8 -> 1400020f…)`. Run `20261106-105958` (the defaults, build `8b8031ee`): that line, `window: 1920x1080`, `WindowCrop 0,0 1920x1080`, 59.7 fps at the title with no crash; run `20261106-105417` (the same write, under the switch's first spelling, with `DM_WINDOW_SIZE=original`) gave `WindowCrop 0,0 2048x1152`, 59.7 fps. The title draws no 3D, so neither run shows the controller's effect.
- **Is the controller's input distorted by the host? (open).** Not shown. The host answers a timestamp report with the time its submission completed (`gpu_timestamps submission`, the default; `vka_exec.c` `post_run`), the same for every report of one submission. The title makes 6 submissions a frame, so the frame's first and last reports are in different submissions, and their difference spans from the first submission's end to the last one's end: on hardware it would span from the first one's start, and here it also takes in the replay worker's translation of the submissions between them, which hardware does not have. So the game can read more GPU time than the phone's GPU spends when the replay's recording time is large (Mario Kart World's is 9-15 ms a frame); `gpu_timestamps segment` would give each report its place inside its submission but would keep the time between submissions. Nothing reads the controller's values on Android (the probes are Mac only).
- **To check once the 3D scene draws** (after the shader library rebuild): (1) default run, `bn-oot test -t 120` to a 3D scene: the log's `dynamic resolution: off, full resolution`, the 3D targets' size in the `[vk] target WxH` lines (expected the output size, 1920x1080 at the launcher's default), fps and GPU ms from `nxctl.sh stats`; (2) the same route with `-e DM_DYNAMIC_RESOLUTION=1`: the 3D targets' size, whether it sits at its floor (854x480) while the GPU time per frame (`stats`) is well under 16.7 ms, which would be the distortion above, and then with `-e DM_NVN_GPU_TS=segment` too; (3) `-e DM_WINDOW_SIZE=1600x900` and `1280x720` against 1920x1080: the scene's size and fps, as Mario Kart World's table.

## Memory

Read from the code, then measured on the phone ([Boot (Android)](#boot-android)): the heap request is 6.20 GB in the 7.5 GB heap region, as computed; the alias region's high-water mark was +2.09 GB at the title and **+3.75 GB of 5 GB** after the menu's next movie (2.0 GB mapped), so 5 GB may be short in game (open: watch `[mem] alias region mapped up to`).

- **The heap.** `nninitStartup` (`main+0x260bb10` in v131072, `+0x25bbbf0` in the base) sets the heap to `align_down(total − used, 2 MB) − 0xaf200000` (`0xb0a00000` in the base) from `QueryMemoryInfo`, hands the whole heap to `AllocateMemoryBlock`, and takes 36 MB of it for an allocator of its own. With the 9 GB pool and the host's 64 MB of used memory the request is 0x18ce00000 (6.20 GB). The heap region is 7.5 GB, so the request fits with 1.3 GB to spare; the rewritten modules (about 105 MB) leave `SetHeapSize`'s check against the pool far from its limit, so no `mem_used`.
- **The alias region.** The 2.74 GB `nninitStartup` keeps out of the heap is the game's memory beside it; with virtual address memory on, regions it maps in the alias region are its likely user, as on Mario Kart World (not traced). The SDK's AddressRegionManager constructor (`sdk+0x16ba30` in both builds) keeps the 1 GB node area (`mov w8, #0x3fe00000` at `+0x16ba48`, the occupied length at `+0x16bad4`) at the start of the alias region. 5 GB holds the node area, the 2.74 GB and 1.26 GB for fragmentation.
- **No SDK cut.** VammManager::AllocateAddressRegion (`sdk+0x16bb80`) aligns a region to 64 KB under 2 MB and to 2 MB above, with no 1 GB class, so the "2 MB alignment of large regions" cut has nothing to do; the node area cut ("1 GB → 62 MB") would only matter if 5 GB proved short, which is not shown. The shared rules' fingerprints do not match this implementation, as expected.
- **The pool.** 9 GB is not read from the game: the NPDM's system resource is address-space bookkeeping, not a pool size. Whether the game's own heaps fit in 6.2 GB and its regions in the alias region is open until a run (`[mem]` lines, `DM_REGIONS`, `SetHeapSize OOM`).
