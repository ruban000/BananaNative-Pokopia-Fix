# Mario Kart World (`0400C3F00006E000`)

A Switch 2 game: version 1.8.0, from a dump of one Application content (version 0) that carries the 1.8.0 code and data, with no separate update. SDK 21.4.0 built for the Switch 2 (`sdk` names its spec `Ounce`), NVN2. Nintendo EPD's engine (sead / agl / gsys, Phive, Havok 2023.2), modules `main` + `subsdk0` (NintendoSDK movie) + `subsdk1` (`nn::ecli`, Nintendo's embedded Mono runtime) + `sdk`. **Plays on Android** (current: 1.8.0 on a 16 GB phone, checked 2026-11-08; Supported on the player pages; needs a 16 GB phone, `readiness.tsv`). Earlier (resolved): the base build stopped at its first frames on the Mac and the arm64 Android emulator on its sparse textures, and on the phone its image allocations ran out ([Open](#open)); see [Boot (Android; 1.8.0)](#boot-android-180). Its closest relative here is [Donkey Kong Bananza](../040074A01BF12000/README.md) (same engine, NVN2, Ampere shader code).

## Boot (Android; 1.8.0)

Phone, 2026-11-03 (Honor PNM-N49, Adreno 840, system driver; test app `dev.nxnative.android.mkw` from `android-mkw2` f68cff94, `-PnxApp=mkw`; pack `Switch2/0400C3F00006E000-work/android-pack-1.8.0`, the dump at `Switch2/MarioKartWorld/base`, a new save folder): the modules load (subsdk0 and subsdk1 at their own bases, 924 of sdk's symbols bound to earlier modules), the heap is 7.47 GB in a 7.50 GB heap region (the formula above held), `nnMain` starts, the RomFS mounts, NVN2 device API 231.30 (SDK 21), and then, within 2 s of `nnMain`, the main thread stops: `CRASH sig=11 addr=0x20 pc=main+0x69c020`, right after it started the "Prepare Thread" (last svc 0x9). No frame, no image made, so the image allocations were not reached; RSS was not sampled (the process ended inside the first 2 s window).

- The fault: `main+0x69bfd0` (a virtual function, slot 0xc0 of the vtable at `main+0x367a9e0`) loads the global at `main+0x37be900` (through the GOT slot `main+0x36d3a48`) and calls through its +0x20 without a null check; the global was still 0. **Cause (resolved):** the game creates its graphics system, the object that global holds, only when NVN reports major 231 and minor 39 or more (`main+0xdd0890`, then the 0x260-byte allocation and the store at `main+0xdd0900`), and the host answered 231.30. NVN2's versions move with the SDK (21.4.0's sdk answers 231.39 and GPU code minor 20); the host now reads them from the game's own `sdk` (`dm_sdk_nvn2_item`, from upstream nxnative c8521eeb: [The Switch 2's device values](../../../docs/reference/nvn-objects.md#the-switch-2s-device-values)). Not a scheduling problem: the reader and the writer are both on the main thread.
- After that fix (a772aae3; retries m2-m4, 2026-11-03): NVN reports 231.39, the graphics system comes up (window 3840x2160, 3 textures; 2.83 GiB of pools placed, 60 pools, RSS 6.6-6.8 GB within 8 s), and the boot stopped in turn on three SDK calls that reach services the host does not serve: `nn::hid` Jcms / Nmouse (abort 0xe15; hooked, e37131ab), `nn::chat::AttachToRoomInfoChangedEvent` (a null read at `sdk+0x6bc148`; hooked with the sharing key calls, ddb59130), and now (current) `nn::chat::CalculateLocalCameraVideoBufferSize` aborts (`sdk+0x6bf2c8`): it checks GameChat's initialize count (`sdk` data through `[sdk+0xe28038]`), which stays 0 because the host takes over `nn::chat::Initialize`. The size itself is pure: it calls `nn::chat::gsv::MakeImagePreference` and `CalculateRequiredBufferMemory` (imports the sdk takes from `main`). **Resolved (a4cb183f):** every GameChat call the game imports is answered as one state, with no camera ([GameChat at boot](../../../docs/reference/services.md#gamechat-at-boot)).
- After that (m5-m12, 2026-11-03, a4cb183f and later): the game sets up its camera storage at boot whatever the chat state (`main+0xd32270` local, `main+0xd31b20` remote: 384x216, 3 pictures each) and makes a texture of each picture through `nvnNativeImage`; it aborts if one fails. Next, its own `nn::camera::Initialize` (`main+0xcdebc0`, called by its camera manager at `main+0xcdc344`) aborted twice. First `nn::gs::sdk::CheckGraphicsSystemInitialized` aborted at `sdk+0x46e8b8`: the sdk's flag is set only by `BootGraphicsSystem`, inside the `nv::InitializeGraphics` the host takes over. Then `nn::camera::sdk::CreateCameraContext` failed with 0x30af3 (no graphics server session). Both are answered now: the check by the host's `nv::InitializeGraphics` (`hle_nv.c`), the context by a host session with zeroed answers (`hle_sf.c` `dm_sf_host_session`; the game sends command 3 "Default" and command 21 on it).
- The renderer then runs: save mounted, audio out, the replay worker, bindless tables, 29,324 images, the first render targets (1280x720, 2560x1440, 1024x8192). No frame was presented before the phone ran out of memory, 11-14 s in. Either `MemAvailable` fell under 700 MB (the run script's stop) or the low-memory killer ended the game process (m9, m10). The `memory:` lines (m12) at that point: 4,494 MiB of placed pools, 3,204 MiB of images (sparse images counted at their full virtual size), and 1,488 MiB of upload scratch, all of it held by the submission being recorded ([Upload staging grows within one Vulkan submission (Android)](../../../docs/reference/memory.md#upload-staging-grows-within-one-vulkan-submission-android), resolved in 9d48710d: see the next item). The game process had PSS 6.1-6.7 GB. `MemAvailable` was 4.8-5.4 GB at launch, with the phone's other apps resident.
- VmRSS overstates the game: each placed pool block is mapped twice, at its guest address and at the driver's own map, and RSS counts both (m7 smaps: 8.59 GB RSS but 4.3 GB PSS in `/dev/kgsl-3d0`). The run script now stops on PSS (10 GB) and on `MemAvailable` under 700 MB, not on RSS.

## Render resolution (Android; 1.8.0)

Current, 2026-11-04. The game does not render at its window's size. The swap chain is 3 × 3840x2160 (RGBA8, 95 MiB) in both operation modes. The 3D scenes are drawn at a size that follows the operation mode and the Switch 2 graphics scale. Its display state reads that scale through `oe::GetCurrentGraphicsScale` at `main+0x8728f4`, beside `GetOperationMode` and `GetPerformanceMode`. The game shows that size as the window crop (`[nvn] WindowCrop`), and its final composite stretches the scene to the crop.

| mode, graphics scale | crop after start | how it is set |
|---|---|---|
| handheld, 0 | 1920x1080 | `DM_OPMODE=0` (the host's handheld answer) |
| docked, 1 | 2048x1152 (2560x1440 for the first frames) | the default |
| docked, 2 | 1706x960 | `DM_GRAPHICS_SCALE=2` |
| handheld, 2 | 1280x720 | `DM_OPMODE=0 DM_GRAPHICS_SCALE=2` |

## Frame rate (Android; 1.8.0)

The framework picks each frame's interval, 1 or 2 vsyncs, which the game steps by: the function at `main+0x69cbb0` (the base game's `main+0x3a9e28`, found by nxnative), its mode at `[x19+0x210]` (1 = 60 fps, 2 = the game's 30 fps mode, 0 = chosen from the frame's CPU time alone: 1 + the CPU time over the interval, summed at `[x19+0x218]`, divided by a period, kept to 1 or 2), the interval at `[x19+0x214]`, added to the vsync counter the game steps by (`main+0x37c8438`). Frames that waited on the GPU kept interval 1 and played in slow motion: on an AYN Thor (Snapdragon 8 Gen 2, Adreno 740, Turnip) the game held about 45 fps at about 75 % of real speed (Forgejo #63). With `fps_target 60` the interval is the host's frame step, at most 3 (the host's most), and the game's own 30 fps mode stays its own ([A fixed frame step plays in slow motion when frames run long](../../../docs/reference/frame-rate.md#a-fixed-frame-step-plays-in-slow-motion-when-frames-run-long)): a stub placed by its function's fingerprint ([`patches.py`](patches.py), [Frame-step stubs placed by their function](../../../docs/reference/rewriter.md#frame-step-stubs-placed-by-their-function)). nxnative's rule for the base game does not match 1.8.0's main (none of its 96 functions of 0x290 bytes has the fingerprint); 1.8.0's function, 0x28c bytes, has the same mode load and interval store, 0x9c bytes apart, 4 bytes later than in the base game.

- Current: 1.8.0's main rewritten for Android with the stub (`rewrite_main.log`: the function matched at `0x69cbb0`; its fixups name the state page; the other modules byte for byte as the phone's own Prepare made them). The frame step's own count is the log's `[nvn] frame step: game time … (… of real time)` line every 1,800 presents; a Time Trial's clock against real time checks the game's own time (below).
- Pacing (current, 2026-11-09): `fps_hold off`. At the 60 fps cap every frame is shown as soon as it is ready, and the step pays back what a late frame took beyond its vsync, up to 3 at once ([Late frames at a fixed hold paid back in full](../../../docs/reference/frame-rate.md#late-frames-at-a-fixed-hold-paid-back-in-full)). With the holds on (the default before), a race's frames of 1 to 2 vsyncs were held 2 vsyncs after three late frames: a Time Trial's start line (1,980 draws, GPU 15 ms) ran at a steady 30 fps; with the holds off it ran at 51-54 fps, 0.999 of real time by its clock. The 30 fps cap holds every frame 2 vsyncs, for even motion at 30; `DM_FPS_HOLD=on` brings the holds back at 60. The in-game panel offers 60 and 30 ([`dm_fps_lock_rates`](../../../dm/host/hle_fpslock.c)).
- Measured on an AYN Thor (Adreno 740, 16 GB, Android 13; Turnip v27.0.0-R1, Phone 720p, fast cores, instanced draws), a Time Trial's clock against real time (game-frame screenshots 60 s apart, about 0.2 % accurate), the kart at its start:
